# LightQuant Strategy Toolkit

一个技能覆盖策略开发、修复、平台转换和代码解读，当前只支持聚宽（JoinQuant）与 PTrade。先识别用户要完成的工作，再只读取相关参考文档。不要为了通用化而假设两个平台的 API、回测行为或运行环境完全一致。

## 工作类型

- **开发或修改**：新建策略、增补指标/信号/调仓/风控、修改现有策略。沿用原策略意图，按目标平台原生方式实现。
- **调试或加固**：定位 API、生命周期、数据形状、编码、订单状态和回测运行问题。先解决会中断运行或造成状态漂移的硬问题，再处理可跳过的软限制。
- **平台转换**：在聚宽与 PTrade 之间转换。转换行为和语义，不做逐字 API 替换；先归纳源策略不变量，再映射目标平台。
- **代码解读**：把代码翻译为面向普通读者的中文策略说明。除非用户明确要求，不修改、优化或修复代码。

用户同时提出多种工作时，按其目标组合工作，并明确哪些部分是代码事实、平台限制或近似实现。

## 开始前

1. 确认任务类型、目标平台、代码文件和用户希望的交付格式；仅凭代码证据判断平台，不凭文件名或注释猜测。
2. 读取完整的相关策略路径，区分实际被调用的运行逻辑、未调用的备用函数和注释示例。
3. 记录策略不变量：交易范围、筛选/排序、信号、调仓时点、买卖条件、仓位分配、现金处理和风控。
4. 仅在需要时读取下列资料：
   - PTrade：`references/platform-ptrade.md`
   - 聚宽：`references/platform-joinquant.md`
   - 跨平台转换：`references/conversion-matrix.md` 与两个平台参考
   - 策略解读：`references/explanation-dossier.md`
   - 安全、编码和输出约束：`references/safety-and-output-rules.md`
5. 若平台版本、券商部署、回测/实盘环境或 API 能力影响实现，先从策略代码、用户提供的 API 文档或运行日志核实。无法核实则标注未知并采用保守处理，不伪称 API 一定可用。

## 策略开发与修复

### 保留意图

修改前概括并保持用户原有的：

- 资产类型和候选标的来源
- 指标、因子、过滤与排序
- 买入、持有、卖出和调仓条件
- 调仓时间和运行频率
- 单票/总仓位、现金分配和防御处理
- 止盈、止损、回撤或其他风险规则

只在用户要求时改变交易语义或优化收益参数；不要把工程修复包装成投资建议。

### 硬故障优先

优先修复可能导致策略停止、错误交易状态或掩盖故障的问题：

- 语法错误、回调签名错误、目标平台不存在的 API
- 空数据、缺列、无效价格、异常返回形状未处理
- 未初始化的平台状态、日计数在分钟回调中重复递增
- 订单失败后仍更新买入日期、持仓状态、次数或目标列表
- 再平衡、止损止盈、补仓、清仓等辅助下单路径缺少保护
- 中文源文件编码错误或注释/日志乱码

现金不足一手、停牌、涨跌停、没有信号、非调仓日和空候选池通常属于可说明并跳过的软限制；不要为消除每条平台警告而改写策略。

### 实现约束

- 使用目标平台原生生命周期、数据与交易能力，不混用另一平台独有对象或函数。
- 将选股/信号、目标持仓、订单执行、持仓状态和风控尽量分开。
- 新增状态在初始化入口中赋初值，明确每日或每次调仓时何时重置。
- 只有订单返回结果能支持成功判断时才更新交易状态；不要将委托提交误报为成交。
- 对行情、财务和持仓返回值做空值、缺字段、短序列及数据结构检查。
- 所有交易路径都要评估停牌、无效价格、涨跌停、可用资金、可卖数量和目标数量无变化等条件。
- API 能力不确定时，查阅平台参考和用户提供文档；缺少足够证据时明确说明限制，不发明函数或参数。
- 诊断日志简短、有节流，并说明平台边界、关键数量、跳过原因或订单状态。

## 跨平台转换

仅支持聚宽与 PTrade 两个方向。

1. 阅读完整源代码，整理策略不变量，并确认源平台/目标平台及回测或交易环境。
2. 对照 `references/conversion-matrix.md` 映射生命周期、调度、日期、证券代码、行情/财务数据、订单、账户持仓、日志、状态和编码。
3. 逐项确认目标平台 API 是否存在、适用环境和数据返回结构。对不能等价映射的字段或行为，记录近似、降级或阻塞原因。
4. 防止未来数据：财务数据必须按目标平台在当时可获得的披露时间/数据快照处理；不得用后来公告或当前实时数据回填历史决策。
5. 转换后说明语义保持项、差异、无法确认的能力和用户需要在平台侧确认的事项。不要宣称代码等价，除非证据充分。

## 代码解读

### 解释规则

- 只解释代码表达的行为；不预测收益、不推荐证券、不补写策略逻辑。
- 未明确的值写“代码中未明确给出”。被定义但未进入实际调用流程的代码写“代码中存在，但正式运行流程未启用”。
- 评论乱码时不把乱码当作结论依据；使用可解析的条件、调用关系和数据访问佐证。
- 尽量提取明确参数：持仓数、调仓时间、指数、窗口、阈值、成本、滑点、现金公式等。
- 普通读者章节以中文业务动作描述，不把函数、变量、API 或参数名当作解释主体。技术标识仅放在“平台识别依据”“平台 API 识别”“代码依据”及必要的转换风险中，并附中文用途。
- 区分个股/单标的风控、市场风控、交易可达性风控和现金/防御机制；趋势卖出不等于固定止损。

### 默认输出

除非用户另有要求，为每个策略输出一个 Markdown 表格，列为 `模块 | 固定字段 | 策略翻译`，按以下 42 项的顺序填写。每格写一至两句高信息量中文；技术标识不得进入普通阅读路径。

| 模块 | 固定字段 |
|---|---|
| 策略档案 | 1. 策略名；2. 平台；3. 策略类型；4. 识别置信度 |
| 运行流程 | 5. 初始化；6. 盘前；7. 盘中；8. 调仓；9. 尾盘；10. 收盘后 |
| 选标的逻辑 | 11. 交易范围；12. 过滤条件；13. 排序因子；14. 信号生成；15. 目标标的形成 |
| 买入逻辑 | 16. 触发条件；17. 买入对象；18. 下单方式；19. 资金分配；20. 买入限制 |
| 卖出逻辑 | 21. 调仓卖出；22. 止盈；23. 止损；24. 特殊情况卖出 |
| 仓位与资金管理 | 25. 目标持仓数；26. 单票金额；27. 总投入上限；28. 现金处理；29. 等权/加权方式 |
| 风控与防守逻辑 | 30. 个股/单标的风控；31. 市场风控；32. 交易可达性风控；33. 空仓/防御机制 |
| 交易成本与执行假设 | 34. 滑点；35. 交易费用；36. 最低佣金；37. 成交假设 |
| 关键风险点 | 38. 回撤；39. 过拟合；40. 流动性；41. 换手；42. 参数敏感性 |

平台识别要基于启动流程、调度、行情/财务访问、交易动作、账户字段或证券代码格式等实际证据，并注明置信度。可应用户要求添加“平台 API 识别”“跨平台转换风险”“代码依据”或测试评分，但不让可选技术章节替代固定档案。

## 输出与验证

- 开发、调试或转换时，简述改动及原因、验证方式、未解决的平台限制；代码解读时按用户所需格式给出结论和证据。
- 运行与任务直接相关、且当前环境可执行的最小验证；不得把本地静态检查表述成平台回测或实盘验证。
- 用户没有要求测试时，不为本技能新增测试套件或扩大验证范围。
- 如需 Excel 档案，先确保“总览”和“策略翻译”均为普通中文；API、变量名和转换风险放到独立技术证据区域。
- 遵守 `references/safety-and-output-rules.md`。
